       - `verification_type`: "automatic" (default)
       - `side_effect_class`: "none" (default, unless goal mentions deploy/delete/send)

Create `src/projects/notify-user-wire.ts` with:

1. `CreateNotifyUserFnOpts` type:
```typescript
export type CreateNotifyUserFnOpts = {
  /** Function that sends a message to the user's session. Typically wraps gateway sessions_send RPC. */
  sendFn: (opts: { sessionKey: string; message: string }) => Promise<void>;
  /** Default session key to use when the recovery context does not provide one. */
  defaultSessionKey?: string;
};
```

2. `createNotifyUserFn(opts: CreateNotifyUserFnOpts): NotifyUserFn`:
   - Import `NotifyUserFn` from `./recovery-manager.js`
   - Return an async function that:
     - Determines session key: use `notifyOpts.sessionKey` if provided, fall back to `opts.defaultSessionKey`, skip notification if neither available (log warning)
     - Formats a human-readable escalation message:
       ```
       Task ${taskId} requires attention.
       Failure: ${failureCategory} - ${failureReason}
       Recovery attempts: ${recoveryAttempts}
       ${workflowId ? `Workflow: ${workflowId}` : ""}
       ```
     - Calls `opts.sendFn({ sessionKey, message })` wrapped in try/catch
     - On sendFn error: log warning with error details but do NOT throw (escalation notification failure should not crash recovery)

This factory pattern keeps the projects/ layer decoupled from the gateway layer. The gateway wires `sendFn` to its sessions_send RPC when creating the recovery manager deps. The projects/ layer only depends on the `sendFn` contract, not on gateway internals.

Per Phase 4 CONTEXT.md D-05 and Research Pitfall 6: this replaces the log-only `defaultNotifyUser` stub so escalation notifications reach users.
