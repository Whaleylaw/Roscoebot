# Phase 6: Progress & Observability - Research

**Researched:** 2026-03-30
**Domain:** Index generation, CLI status output, Gateway RPC, Lit board UI
**Confidence:** HIGH

## Summary

Phase 6 adds workflow progress visibility to four existing surfaces: (1) `.index/workflows/` JSON files generated by SyncService, (2) inline workflow section in `project status` CLI command, (3) `projects.workflows.list` and `projects.workflows.get` Gateway RPC methods, and (4) `[WF-NNN]` badge on board task cards. All four integrate into well-established patterns with clear extension points. No new libraries, frameworks, or external dependencies are needed.

The codebase already has `readWorkflowTaskStatuses()` in `workflow-status-hook.ts` that reads a workflow file and collects all linked task statuses -- this is the core computation needed for index generation. The index generator, sync service, gateway RPC handlers, status command, and board UI each have clean patterns to follow. This is a mechanical extension phase.

**Primary recommendation:** Follow existing patterns exactly -- add `generateWorkflowIndex()` alongside the other `generate*Index()` functions, wire SyncService watcher for `workflows/` directory, extend the status command's text and JSON output, add two RPC handlers mirroring `board.get`/`queue.get`, and add a workflow field to `BoardTaskEntry` for badge rendering.

### Anti-Patterns to Avoid
- **Re-reading task files in RPC handlers:** RPC methods MUST read from `.index/workflows/` JSON files, not parse markdown on every request (D-08)
- **Splitting workflow status into a separate command:** Decision D-01 explicitly locks this as inline in `project status`
- **Adding workflow grouping to the board:** D-10 keeps the board task-focused; workflow progress is surfaced through status/index only
- **Computing progress in the status command:** Progress computation belongs in `generateWorkflowIndex()` which writes to `.index/`; the status command reads from there or computes inline from task file reads (the status command currently reads task files directly, so either approach works for the command -- but index files are the canonical source for RPC)

## Common Pitfalls

### Pitfall 1: Missing Workflow Directory in SyncService
**What goes wrong:** SyncService watches `projectsRoot` with depth 5, but `processUpdate()` only handles `PROJECT.md`, `queue.md`, and `tasks/TASK-*.md`. Workflow file changes silently get ignored.
**Why it happens:** The chokidar watcher already sees workflow file changes, but the `processUpdate()` routing has no `workflows/` branch.
**How to avoid:** Add an `else if (relative.startsWith("workflows/"))` branch in `processUpdate()` that triggers workflow index regeneration.
**Warning signs:** Workflow files change on disk but `.index/workflows/` JSON files are stale.

### Pitfall 2: Board Index Missing Workflow Field
**What goes wrong:** The board UI expects `task.workflow` to render the badge, but `BoardTaskEntry` in `sync-types.ts` does not include a `workflow` field, and `generateBoardIndex()` does not populate it.
**Why it happens:** `BoardTaskEntry` was created before workflow support existed.
**How to avoid:** Add `workflow?: string | null` to `BoardTaskEntry` in both `src/projects/sync-types.ts` AND `ui/src/ui/controllers/projects.ts`, and populate it in `generateBoardIndex()` from `TaskFrontmatter.workflow`.
**Warning signs:** Board cards render but no workflow badge appears.

### Pitfall 3: Stale Workflow Index After Task Changes
**What goes wrong:** A task completes, the workflow status hook updates the workflow file, but the workflow index still shows old progress counts.
**Why it happens:** The task change triggers a task index + board rebuild, but not a workflow index rebuild. The workflow status hook writes to the workflow file, which should trigger a separate SyncService event.
**How to avoid:** The workflow status hook already writes to the workflow `.md` file atomically. SyncService's chokidar watcher will detect this change and trigger workflow index regeneration -- as long as the `processUpdate()` routing handles `workflows/` files. No extra wiring needed beyond Pitfall 1.
**Warning signs:** Workflow progress counts lag behind actual task completions.

### Pitfall 4: generateAllIndexes Missing Workflow Reindex
**What goes wrong:** Full reindex on startup (`generateAllIndexes()`) generates project/task/board/queue indexes but not workflow indexes. After a gateway restart, workflow index files are missing until a workflow file changes.
**Why it happens:** `generateAllIndexes()` needs to be extended to also read `workflows/` directory and generate workflow indexes.
**How to avoid:** Add workflow index generation as step 5 in `generateAllIndexes()`.
**Warning signs:** After gateway restart, RPC calls to `projects.workflows.list` return empty results until a workflow file changes.

### Pitfall 5: WebSocket Broadcast Missing workflow:changed
**What goes wrong:** The UI does not receive live updates when workflow status changes.
**Why it happens:** `ProjectGatewayService.handleSyncEvent()` has a switch statement that does not handle the new `workflow:changed` event type.
**How to avoid:** Add a `case "workflow:changed":` in `handleSyncEvent()` that broadcasts `"projects.workflows.changed"`.
**Warning signs:** UI shows stale workflow data; requires manual refresh.

### Pitfall 6: Status Command File-Based vs Index-Based Read
**What goes wrong:** The status command already reads task files directly (not from `.index/`). For consistency, workflow progress in the status command should also read workflow files directly, OR read from `.index/workflows/`. Mixing approaches creates confusion.
**Why it happens:** The existing status command was built before the index system and reads task files directly.
**How to avoid:** For the status command, reading workflow files directly (using the same pattern as task file reads) is simpler and consistent with the current command. For RPC methods, always read from `.index/` per D-08.
**Warning signs:** Progress counts differ between status command and UI.

### generateWorkflowIndex (Recommended Implementation Sketch)

```typescript
// Source: planned addition to src/projects/index-generator.ts

export function generateWorkflowIndex(
  frontmatter: WorkflowFrontmatter,
  taskStatuses: Map<string, string>,
): WorkflowIndex {
  let done = 0, claimed = 0, review = 0, blocked = 0, available = 0;
  for (const [_taskId, status] of taskStatuses) {
    switch (status) {
      case "done": done++; break;
      case "in-progress": claimed++; break;
      case "review": review++; break;
      case "blocked": blocked++; break;
      default: available++; break;
    }
  }
  return {
    id: frontmatter.id,
    title: frontmatter.title,
    status: frontmatter.status,
    goal: frontmatter.goal,
    tasks: frontmatter.tasks,
    template: frontmatter.template,
    progress: {
      total: frontmatter.tasks.length,
      done, claimed, review, blocked, available,
    },
    indexedAt: new Date().toISOString(),
  };
}
```

## Open Questions

1. **Status command: file-based or index-based reads?**
   - What we know: Current status command reads task files directly (not from `.index/`). RPC handlers read from `.index/`.
   - What's unclear: Should the status command also read from `.index/` for consistency, or keep reading markdown files directly?
   - Recommendation: Read workflow files directly in the status command (consistent with existing task reads). Keep `.index/` as the RPC optimization layer. Both approaches yield the same data.

2. **WorkflowSummary: flat list or with aggregates?**
   - What we know: D-04 specifies `.index/workflows.json` summary file. D-05 specifies per-workflow progress.
   - What's unclear: Whether the summary file should include project-level aggregates (total active workflows, total tasks across all workflows).
   - Recommendation: Start with a flat list of workflow summaries (id, title, status, progress). Add aggregates only if needed by consumers. Simpler is better for v1.
